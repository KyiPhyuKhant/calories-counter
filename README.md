# Calorie Counter

An iOS-first React Native app built with Expo, Expo Router, and strict TypeScript.
The app currently contains a welcome screen, an editable profile and calorie
goal calculator, a searchable food catalog, and local SQLite infrastructure.
It does not require an account, server, or network connection to store data.

## Development

Use Node.js 24 LTS (or newer) and npm. Database tests use Node's built-in SQLite.

```sh
npm ci
npm start
```

For the iOS simulator, install Xcode and an iOS simulator runtime, then run:

```sh
npm run ios
```

For a physical device, run `npm start` and open the QR code with a compatible
Expo Go installation on the same network. Expo Go must support this project's
Expo SDK version. Check https://expo.dev/go for available builds; iOS App Store
availability can differ from simulator builds. If no compatible physical iOS
Expo Go build is available, a development build will be needed.

## Validation

```sh
npm run typecheck
npm run lint
npm test
npx expo install --check
npx expo export --platform ios
```

## Structure

- `src/app/`: Expo Router route entries and root navigation layout.
- `src/screens/`: Screen content, kept separate from navigation.
- `src/theme/`: Shared colors and spacing.
- `src/domain/`: Pure calorie equations, validation, and target guardrails.
- `src/components/`: Shared food form fields and catalog presentation.
- `src/data/`: Database initialization, versioned migrations, typed repositories,
  and the provider that makes repositories available with `useRepositories()`.
- `tests/`: Real SQLite verification of migrations and repository behavior.
- `app.json`: Expo configuration.

Native `ios/` and `android/` directories are generated by Expo when needed and
are ignored. Keep local secrets in ignored `.env` files. Variables prefixed
with `EXPO_PUBLIC_` are bundled into the app and must never contain secrets.

## Local database

`calories-counter.db` is created in Expo SQLite's default app-local directory.
Startup enables WAL and foreign keys, then applies ordered migrations inside a
transaction using `PRAGMA user_version`. New schema changes must append a
migration; do not edit migrations already released. Initialization errors block
the app and offer a retry without deleting existing data.

There is one local profile. UUIDs identify records; food nutrition is expressed
per 100 grams, portions in grams, height in centimeters, and weight in kilograms.
Repository timestamps are normalized to UTC ISO strings. Diary entries and
planned meals copy the food name and nutrition when created. Catalog edits or
deletions preserve those snapshots. Plans are never counted as consumed entries.
Profile deletion is restricted while related records exist.

Tests execute the production migration SQL and repository queries through a
Node SQLite adapter. They do not exercise Expo's native bridge or simulator UI.

## Calorie estimates

Open **Set up your profile** on the welcome screen to enter or edit your profile.
The profile and optional manual target are saved locally. Migration 2 preserves
existing profile IDs and leaves new fields unset until the user completes them.
Suggested targets are derived from the saved inputs, not stored as stale totals.

Mifflin-St Jeor estimates resting energy expenditure (shown as estimated BMR):
`10 * currentWeightKg + 6.25 * heightCm - 5 * age + sexConstant`, where the
constant is `+5` for the male equation and `-161` for the female equation.
TDEE is that estimate multiplied by the selected activity factor. These are
predictions, not measured calorie burn, and target weight does not enter them.

| Activity | Factor | Approximate description |
| --- | --- | --- |
| Sedentary | 1.2 | Little exercise |
| Light | 1.375 | Exercise 1-3 days/week |
| Moderate | 1.55 | Exercise 3-5 days/week |
| Very active | 1.725 | Hard exercise 6-7 days/week |
| Extremely active | 1.9 | Physical work and intensive training |

App policy: loss subtracts the smaller of 15% of TDEE or 500 kcal/day;
maintenance uses TDEE; gain adds the smaller of 10% or 300 kcal/day.
Targets are rounded to whole kcal and constrained to a range. The lower bound
is the highest of estimated BMR, 80% of TDEE, TDEE minus 500, and an intake floor
of 1200 for the female equation or 1500 for the male equation. Low current BMI
also raises the lower bound to TDEE. The upper bound is the lower of 6000 or
TDEE plus the smaller of 15% or 500. Manual overrides follow the same limits;
switching off manual adjustment restores the suggestion.

These conservative app rules are not individually prescribed medical limits.
The calculator supports ages 18-100, heights 120-230 cm, and weights 35-300 kg.
It rejects nonfinite numbers, fractional ages, contradictory goal directions,
targets below an adult BMI screening threshold of 18.5, and weight-loss goals
at a low current BMI. Cases outside the calorie range require individual advice.
It is not intended for pregnancy or breastfeeding. BMI is only a screening
guardrail, and calculated targets cannot guarantee clinical suitability.

Sources:
- [Original Mifflin-St Jeor study](https://pubmed.ncbi.nlm.nih.gov/2305711/).
- [Activity factor table in a clinical nutrition tutorial](https://doi.org/10.1016/j.clnesp.2024.07.1055).
- [AHA/ACC/TOS adult weight-management guideline](https://pmc.ncbi.nlm.nih.gov/articles/PMC5819889/).
- [CDC adult BMI categories](https://www.cdc.gov/bmi/adult-calculator/bmi-categories.html).
- [NIDDK calculator population guidance](https://www.niddk.nih.gov/health-information/weight-management/body-weight-planner).

## Food catalog

Open **Browse foods** to search the local catalog, view serving nutrition, or add
a custom food. Only custom foods can be edited or deleted. Catalog searches use
SQLite FTS5 with Unicode tokens, accent folding, and prefix matching for each
word. Searches are parameterized, pagination is deterministic, and insert,
update, and delete triggers keep the index synchronized.

Migration 3 adds four bundled development samples. All sample values are
invented and explicitly labeled as unverified in the list, details, and notes.
They are demonstration data, not nutritional guidance. Each has a stable ID and
is inserted once by the migration.

Nutrition is stored per declared serving amount/unit. Optional macros remain
`NULL` when unknown, rather than being reported as zero. Serving calculations
scale these values; mass conversions support grams, kilograms, and ounces.
No density is assumed for milliliters, cups, pieces, or generic servings.
Existing gram-based diary operations reject foods without a mass conversion;
food tracking UI is not part of this step. Existing historical snapshots and
food links survive the migration, and catalog edits do not rewrite snapshots.

Custom duplicates are rejected for the same normalized name, serving amount,
and unit. Preexisting duplicate records are preserved during migration. External
foods are deduplicated by provider and provider ID, keeping stable local IDs.
`src/data/foodProvider.ts` defines a future integration contract and the food
repository can persist supplied external records for offline search. No live
provider, USDA connection, online search, or API credentials are implemented.

To verify search, custom-food CRUD, migration preservation, and serving math:

```sh
npm test
npm run typecheck
npm run lint
```

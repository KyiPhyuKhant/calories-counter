# Calorie Counter

An iOS-first React Native app built with Expo, Expo Router, and strict TypeScript.
The app currently contains a daily dashboard, an editable profile and calorie
goal calculator, a searchable food catalog, a daily food diary, and future meal
planning and weight/calorie history backed by SQLite.
It does not require an account, server, or network connection to store data.

## Development

Use Node.js 24 LTS (or newer) and npm. Database tests use Node's built-in SQLite.

```sh
npm ci
npm start
```

For the iOS simulator, install Xcode and an iOS simulator runtime, then run:

```sh
npm run ios
```

For a physical device, run `npm start` and open the QR code with a compatible
Expo Go installation on the same network. Expo Go must support this project's
Expo SDK version. Check https://expo.dev/go for available builds; iOS App Store
availability can differ from simulator builds. If no compatible physical iOS
Expo Go build is available, a development build will be needed.

## Validation

```sh
npm run typecheck
npm run lint
npm test
npx expo install --check
npx expo export --platform ios
```

## Structure

- `src/app/`: Expo Router route entries and root navigation layout.
- `src/screens/`: Screen content, kept separate from navigation.
- `src/theme/`: Shared colors and spacing.
- `src/domain/`: Pure calorie equations, validation, and target guardrails.
- `src/components/`: Shared food form fields and catalog presentation.
- `src/data/`: Database initialization, versioned migrations, typed repositories,
  and the provider that makes repositories available with `useRepositories()`.
- `tests/`: Real SQLite verification of migrations and repository behavior.
- `app.json`: Expo configuration.

Native `ios/` and `android/` directories are generated by Expo when needed and
are ignored. Keep local secrets in ignored `.env` files. Variables prefixed
with `EXPO_PUBLIC_` are bundled into the app and must never contain secrets.

## Local database

`calories-counter.db` is created in Expo SQLite's default app-local directory.
Startup enables WAL and foreign keys, then applies ordered migrations inside a
transaction using `PRAGMA user_version`. New schema changes must append a
migration; do not edit migrations already released. Initialization errors block
the app and offer a retry without deleting existing data.

There is one local profile. UUIDs identify records; food nutrition is expressed
per 100 grams, portions in grams, height in centimeters, and weight in kilograms.
Repository timestamps are normalized to UTC ISO strings. Diary entries and
planned meals copy the food name and nutrition when created. Catalog edits or
deletions preserve those snapshots. Plans are never counted as consumed entries.
Profile deletion is restricted while related records exist.

Tests execute the production migration SQL and repository queries through a
Node SQLite adapter. They do not exercise Expo's native bridge or simulator UI.

## Calorie estimates

Open the profile button on the dashboard to enter or edit your profile.
The profile and optional manual target are saved locally. Migration 2 preserves
existing profile IDs and leaves new fields unset until the user completes them.
Suggested targets are derived from the saved inputs, not stored as stale totals.

Mifflin-St Jeor estimates resting energy expenditure (shown as estimated BMR):
`10 * currentWeightKg + 6.25 * heightCm - 5 * age + sexConstant`, where the
constant is `+5` for the male equation and `-161` for the female equation.
TDEE is that estimate multiplied by the selected activity factor. These are
predictions, not measured calorie burn, and target weight does not enter them.

| Activity | Factor | Approximate description |
| --- | --- | --- |
| Sedentary | 1.2 | Little exercise |
| Light | 1.375 | Exercise 1-3 days/week |
| Moderate | 1.55 | Exercise 3-5 days/week |
| Very active | 1.725 | Hard exercise 6-7 days/week |
| Extremely active | 1.9 | Physical work and intensive training |

App policy: loss subtracts the smaller of 15% of TDEE or 500 kcal/day;
maintenance uses TDEE; gain adds the smaller of 10% or 300 kcal/day.
Targets are rounded to whole kcal and constrained to a range. The lower bound
is the highest of estimated BMR, 80% of TDEE, TDEE minus 500, and an intake floor
of 1200 for the female equation or 1500 for the male equation. Low current BMI
also raises the lower bound to TDEE. The upper bound is the lower of 6000 or
TDEE plus the smaller of 15% or 500. Manual overrides follow the same limits;
switching off manual adjustment restores the suggestion.

These conservative app rules are not individually prescribed medical limits.
The calculator supports ages 18-100, heights 120-230 cm, and weights 35-300 kg.
It rejects nonfinite numbers, fractional ages, contradictory goal directions,
targets below an adult BMI screening threshold of 18.5, and weight-loss goals
at a low current BMI. Cases outside the calorie range require individual advice.
It is not intended for pregnancy or breastfeeding. BMI is only a screening
guardrail, and calculated targets cannot guarantee clinical suitability.

Sources:
- [Original Mifflin-St Jeor study](https://pubmed.ncbi.nlm.nih.gov/2305711/).
- [Activity factor table in a clinical nutrition tutorial](https://doi.org/10.1016/j.clnesp.2024.07.1055).
- [AHA/ACC/TOS adult weight-management guideline](https://pmc.ncbi.nlm.nih.gov/articles/PMC5819889/).
- [CDC adult BMI categories](https://www.cdc.gov/bmi/adult-calculator/bmi-categories.html).
- [NIDDK calculator population guidance](https://www.niddk.nih.gov/health-information/weight-management/body-weight-planner).

## Food catalog

Open the dashboard's food catalog button to search locally, view serving nutrition, or add
a custom food. Only custom foods can be edited or deleted. Catalog searches use
SQLite FTS5 with Unicode tokens, accent folding, and prefix matching for each
word. Searches are parameterized, pagination is deterministic, and insert,
update, and delete triggers keep the index synchronized.

Migration 3 adds four bundled development samples. All sample values are
invented and explicitly labeled as unverified in the list, details, and notes.
They are demonstration data, not nutritional guidance. Each has a stable ID and
is inserted once by the migration.

Nutrition is stored per declared serving amount/unit. Optional macros remain
`NULL` when unknown, rather than being reported as zero. Serving calculations
scale these values; mass conversions support grams, kilograms, and ounces.
No density is assumed for milliliters, cups, pieces, or generic servings.
The legacy gram-based repository method requires a mass conversion; the daily
diary accepts quantities in each food's declared unit or number of servings.
Existing historical snapshots and food links survive the migration, and catalog
edits do not rewrite snapshots.

Custom duplicates are rejected for the same normalized name, serving amount,
and unit. Preexisting duplicate records are preserved during migration. External
foods are deduplicated by provider and provider ID, keeping stable local IDs.
The USDA integration uses `src/data/foodProvider.ts`; selected external foods
are cached through the same repository for offline search. See setup below.

To verify search, custom-food CRUD, migration preservation, and serving math:

```sh
npm test
npm run typecheck
npm run lint
```

## Daily diary

Open the diary button on the dashboard. Use the previous/next controls,
the native date picker, or Today to select a local calendar day. Each meal has an
add button that opens the existing offline catalog. Select a food, enter an
amount in its declared unit or a fractional number of servings, select a meal,
and log it. Tap an entry to edit quantity, meal, or date; the trash button deletes
the entry after confirmation. The diary displays each meal's calories and the
daily total. No profile setup or account is required to log food.

Migration 4 stores an immutable nutrition basis with the food name, serving
amount/unit, optional macros, notes, source, and provider identity. Totals are
derived from this snapshot and stored with the entry. Editing a diary entry uses
its original snapshot, even after the catalog food changes or is deleted. Food
selection is only needed for new entries. Plans are not included in diary totals.

`entry_date` is an explicit `YYYY-MM-DD` calendar date, independent of the UTC
audit timestamp. Local dates use device calendar components, not ISO timestamp
slicing. Navigation uses calendar-day arithmetic across daylight-saving changes.
The UI supports dates from 1900 through 2100. Legacy entries had only a timestamp:
migration assigns their date using the device timezone once and their meal to
Snacks, preserving their original gram nutrition rather than reading newer
catalog values. Dates remain fixed when the user later changes timezone.

Logging a food and creating the local profile if necessary are transactional.
Quantity edits and recalculated totals are also committed together. Missing
macro values remain unknown. Development samples remain labeled as unverified
after logging. Tests cover meal/day totals, date separation, local midnights in
Tokyo and Los Angeles, DST, migration rollback, historical edits and deletion.

## Daily dashboard

The home screen reads the selected local date's consumed entries and saved profile
in one database transaction. Meal summaries and progress use diary snapshot totals;
planned meals, including plans for the selected day, are never counted.
Remaining calories equal target minus consumed: positive values show remaining,
zero indicates the target is reached, and negative values show the excess.
The accessible progress bar caps at 100%, with a restrained warning color over target.

The current profile's calculated or manual target applies to every selected date;
historical target versions are not stored. Calorie needs remain estimates, not
measured expenditure. An incomplete or invalid profile shows consumed calories
without inventing a target and offers profile setup.

Successful diary and profile mutations notify the focused dashboard after commit.
Returning to it also reloads persisted data. Loading failures offer a retry and
outdated asynchronous reads cannot replace a newer date's result. Dashboard tests
cover all three target states, manual overrides, date and plan exclusion, and
refresh notifications for additions, edits, deletions, and failed writes.

## Meal planning

Open **Meal plans** on the dashboard. The planner starts on tomorrow; its date
picker and previous/next controls also allow viewing earlier plans. Each meal
accepts catalog foods with amounts or fractional servings. Planned-day and meal
totals include every planned item, including items subsequently marked eaten,
and compare against the current saved profile target. They are never consumed totals.

Migration 5 upgrades legacy gram plans to explicit local dates and serving
snapshots without changing their IDs or nutrition. New plans snapshot the food's
name, source, notes, serving basis and optional nutrition. Editing uses the saved
basis, not the current catalog. Unconsumed items can be edited or deleted.

The copy button copies a source day into an empty destination, with new IDs and
uneaten status. It preserves original quantities and snapshots, even for eaten
items or deleted catalog foods. Copying is atomic; occupied destinations are
rejected to avoid accidental duplication, and the source plan is untouched.

The meal's check button opens a confirmation with an explicit date eaten, defaulting
to today. Future consumption dates are rejected. All pending foods in that meal
are logged in one transaction using their planned snapshots. Each plan receives
a durable eaten timestamp/date and a unique link to its diary entry. Repeated
requests skip eaten items, including after app restart. The original plan stays
read-only as history; its consumed entries remain editable in the diary.
Deleting a diary entry clears its link but retains the eaten receipt, so tapping
the original plan again cannot accidentally re-log it. There is no automatic
conversion when a planned date arrives.

Tests cover planning CRUD, snapshot copies, day/meal separation, conversion
idempotency, transaction rollback, migration preservation, and reopen persistence.

## Weight and calorie history

Open **Weight and calorie history** on the dashboard. Weekly periods run Monday
through Sunday; monthly periods use calendar months. The date picker and arrows
select the period. Weight and Calories tabs show their respective summaries and
dated records, with live refresh after repository writes or returning to the screen.

The weight tab records measurements in kilograms on explicit local calendar dates.
New or edited measurements support 35-300 kg and today or earlier dates. Recording,
editing, or deleting a measurement never updates the current profile weight.
Multiple measurements on a date are retained, including legacy duplicates; the
accessible SVG point chart displays their labeled daily mean. Missing dates have
no points and are not interpolated. Every recorded measurement remains available
in the list for editing and deletion. Period average weight uses all recorded
measurements; change compares the first and last observed daily means and is
unavailable without two distinct measured dates.

Migration 6 preserves weight IDs, values and original timestamps, resolving legacy
local dates once. The explicit measurement date remains stable after timezone
changes; the original instant and creation timestamp are retained for auditing.

Calorie history reads consumed diary snapshots only, excluding plans. No entries
means **No food logged**, not a measured zero. A recorded zero-calorie food can
produce a real zero logged total. Period totals and averages use logged days only,
with coverage counts shown; they do not imply a complete intake record. Future
dates are listed but excluded from summaries and target comparisons.

Previous versions did not retain historical targets. This upgrade records the
current profile's valid target on the upgrade date only; earlier targets remain
unknown. Subsequent profile saves atomically record an effective local date and
target, including manual overrides. The final target saved on a date applies to
that day and carries forward until the next change; intraday revisions are not
retained. An incomplete profile records an unknown target rather than carrying a
stale one forward. Under/at/over status requires both logged calories and a known
dated target. The dashboard and planner still use the current profile target;
the history view uses the dated target record. Targets remain estimates.

Tests cover date ranges across DST, leap months and years, missing versus zero
logs, dated targets, all comparison states, weight CRUD and duplicate-day means,
profile independence, transactional rollback, migrations, and reopen persistence.

## USDA online foods

The catalog's **USDA online** mode searches USDA FoodData Central through a small
Node proxy. Saved and custom foods remain offline and do not require the proxy.
Online queries and selected FDC IDs are sent to USDA; profile, weight, diary and
plan data are not sent. Search is explicit, not performed on every keystroke.

### Configuration

Obtain a private key from [USDA's key signup](https://fdc.nal.usda.gov/api-key-signup/).
USDA requires keys to remain private: never use `EXPO_PUBLIC_USDA_API_KEY`, commit
a key, or embed it in an app build. The proxy alone reads the ignored server file:

```dotenv
# .env.server.local (ignored; server only)
USDA_API_KEY=<your-private-key>
FOOD_API_HOST=127.0.0.1
FOOD_API_PORT=4111
```

The app reads only a nonsecret proxy address from `.env.local`:

```dotenv
EXPO_PUBLIC_FOOD_API_URL=http://127.0.0.1:4111
```

Run `npm run food-api` and, in another terminal, `npm run ios`. Restart Expo after
changing configuration. The localhost URL works in the iOS simulator. For an
iPhone on a trusted LAN, explicitly bind `FOOD_API_HOST=0.0.0.0` and use the Mac's
LAN IP in the app's proxy URL. Do not expose this development proxy to the public
internet. Production builds require an HTTPS proxy with deployment-side access
controls and abuse protection; those deployment controls are not supplied here.
No key is needed in Expo Go or on the phone. Missing configuration leaves the
online mode unavailable and the local catalog usable.

### Data and limits

This stage supports Foundation, SR Legacy, and Survey (FNDDS) foods. Search shows
the first 20 provider matches with supported calorie data; refine the query for
other results. Branded/Experimental foods are excluded rather than assuming a
nutrition basis or density. Required energy uses USDA kcal nutrient 1008, then
Atwater specific 2048 or general 2047 when available. Missing energy is not
invented; unknown macros remain null. Results initially use the 100-g basis.
Selecting a result fetches full details; a reported gram-weight portion, when
available, becomes the serving basis and scales all nutrients consistently.
Otherwise the basis remains 100 g. Provider portion descriptions and source links
are retained in SQLite notes. Cached provider IDs are unique, and refreshing a
cached food does not rewrite existing diary or plan snapshots.

The client times out after 12 seconds; the proxy times out after 10. Cancellation
and stale-response guards protect search results. Empty results, malformed data,
network failures, invalid keys, and rate limits have distinct handling. Retry is
manual, and rate-limit cooldowns are honored. The development proxy also limits
aggregate requests to 500/hour in memory. Restarting it resets that local limit;
USDA's limit still applies. USDA documents a normal 1,000/hour/IP limit, and its
public exploration credential has much lower limits. Use a registered private
key for ongoing use. See the [API guide](https://fdc.nal.usda.gov/api-guide/) and
[api.data.gov key/rate guidance](https://api.data.gov/docs/developer-manual/).

USDA data are public-domain [CC0](https://fdc.nal.usda.gov/api-guide/#licensing).
Online and cached foods identify USDA FoodData Central; source links and FDC IDs
remain attached. Nutrition normalization follows the [Foundation Foods
documentation](https://fdc.nal.usda.gov/Foundation_Foods_Documentation/).

### Verification

`npm test` uses explicitly synthetic protocol fixtures, never presented as USDA
data. It covers mapping, portions, missing nutrients, errors, cancellation,
timeouts, key isolation, proxy limits and offline-cache deduplication. Live checks
are separate and require valid server configuration:

```sh
npm run test:provider:live
```

That command makes two real USDA requests (search/details) and verifies caching
in a temporary in-memory SQLite database. It does not touch app data or print the
key. During Step 9, this pipeline was verified using USDA's documented public
exploration credential. No registered private key or deployed production proxy
was available; configure your own key and reachable proxy before using online
search normally.
